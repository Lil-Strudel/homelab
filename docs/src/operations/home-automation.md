# Home Automation

Home Assistant and the services behind it run in one namespace, `home-automation`, from
`kubernetes/apps/home-automation/` under their own Flux Kustomization
(`clusters/main/home-automation.yaml`). The radios are network devices on the Trusted VLAN,
not USB sticks on a node. Why it is built this way is in
[Decisions → Home Automation](../decisions/home-automation.md).

## What runs

| App | Hostname | Does |
| --- | --- | --- |
| Home Assistant | `home.lilstrudel.io` | Devices, automations, dashboards; recorder on its own CNPG cluster |
| Zigbee2MQTT | `z2m.lilstrudel.io` | Drives the Zigbee radio; publishes devices to Mosquitto |
| Z-Wave JS UI | `zwave.lilstrudel.io` | Drives the Z-Wave radio; Home Assistant connects to its websocket server |
| Mosquitto | — (in-cluster) | MQTT broker between Zigbee2MQTT and Home Assistant |

Every hostname is internal: a pinned IP in the `10.69.65.70`–`.72` band in `local.services`,
reachable from the Home VLAN and WireGuard. Mosquitto and the Z-Wave JS websocket (`3000`) are
`ClusterIP` only.

```
Zigbee radio ──tcp──► zigbee2mqtt ──mqtt──► mosquitto ◄──mqtt── home-assistant ──► home-assistant-pg
Z-Wave radio ──tcp──► zwave-js-ui ◄────────── websocket :3000 ──────┘
```

## Radios

| Radio | Hardware | Endpoint |
| --- | --- | --- |
| Zigbee | SONOFF ZBDongle-E (EFR32MG21, EmberZNet), on the interim Pi | `tcp://10.69.60.30:6638` |
| Z-Wave | SONOFF Dongle-PZG23 (Z-Wave 800), on the interim Pi | `tcp://10.69.60.30:6639` |

The Pi runs `ser2net` to put both USB sticks on the network. It is temporary and not managed
as code; the SONOFF Dongle Max (Zigbee) and Dongle-MZG23 (Z-Wave), both PoE, replace it — see
[Swapping a radio](#swapping-a-radio).

Each endpoint is written in **two** places, and both must change together:

- the app's Deployment — `ZIGBEE2MQTT_CONFIG_SERIAL_PORT` in `zigbee2mqtt/deployment.yaml`,
  `ZWAVE_PORT` in `zwave-js-ui/deployment.yaml`;
- the app's `CiliumNetworkPolicy` — the `toCIDR` `/32` and port in the same directory.

Change one without the other and the app crash-loops on a refused connection.

## Secrets

| Secret | File | Holds |
| --- | --- | --- |
| `mqtt-credentials` | `mqtt-credentials.sops.yaml` | The `zigbee2mqtt` and `home-assistant` MQTT passwords |
| `zigbee2mqtt` | `zigbee2mqtt/secret.sops.yaml` | Zigbee network key, PAN ID, extended PAN ID; frontend token |
| `zwave-js-ui` | `zwave-js-ui/secret.sops.yaml` | S0, S2 (×3) and Long Range (×2) keys; UI login; session secret |
| `home-assistant-pg-backup` | `home-assistant/postgres-backup-secret.sops.yaml` | The `homelab-cnpg-home-assistant` IAM key |
| `home-assistant-prometheus` | `home-assistant/prometheus-token.sops.yaml` | The long-lived HA token `vmagent` scrapes with |
| `home-assistant-pg-app` | — (generated by CNPG) | Recorder database credentials |

**The radio keys are permanent.** Every paired device is bound to them; changing one means
re-pairing everything on that radio. Never regenerate them.

Read a value with:

```sh
sops -d kubernetes/apps/home-automation/mqtt-credentials.sops.yaml | yq .stringData.HOME_ASSISTANT_PASSWORD
```

## First-time setup

After Flux brings the namespace up, five things are done once by hand.

0. **Trust the ingress proxy** — only on a brand-new config volume; a restored one already
   has it. Until this is set, `home.lilstrudel.io` answers `400: Bad Request`, so reach Home
   Assistant directly instead:

   ```sh
   kubectl -n home-automation port-forward deploy/home-assistant 8123
   ```

   At `http://localhost:8123`, onboard (step 1), then under *Settings → System → Network →
   HTTP server* turn on *Trust X-Forwarded-For* with trusted proxy `10.244.0.0/16`. Home
   Assistant restarts with the change as a trial: **confirm it within five minutes** or it
   reverts. Why it is not in YAML is in
   [Decisions → Home Automation](../decisions/home-automation.md#reverse-proxy-trust-is-in-storage-not-yaml).
1. **Onboard Home Assistant** at `https://home.lilstrudel.io`: create the owner account, then
   set the home location, units and time zone. These live in the UI, not git — the repo is
   public.
2. **Add the MQTT integration** (*Settings → Devices & services → Add integration → MQTT*):
   broker `mosquitto`, port `1883`, username `home-assistant`, password
   `HOME_ASSISTANT_PASSWORD` from `mqtt-credentials`. Zigbee2MQTT devices appear through MQTT
   discovery from then on.
3. **Add the Z-Wave integration** (*Add integration → Z-Wave*): when it asks, decline the
   add-on and enter `ws://zwave-js-ui:3000`.
4. **Turn on Z-Wave JS UI's login** (*Settings → General → Auth*). It logs in with
   `DEFAULT_USERNAME` / `DEFAULT_PASSWORD` from `zwave-js-ui`. Until this is on, the UI is
   open to anyone on the Home VLAN, so do it first. While there, enable scheduled NVM
   backups (*Settings → Backup*); they land in the store volume, which Velero copies.
5. **Log in to Zigbee2MQTT** with the frontend token, `ZIGBEE2MQTT_CONFIG_FRONTEND_AUTH_TOKEN`
   from `zigbee2mqtt`.

## Metrics

`vmagent` scrapes Home Assistant's `/api/prometheus` every minute (`home-assistant/scrape.yaml`):
one series per entity — sensor readings, switch and light states, availability — under the
`homeassistant_` prefix, plus the process's own Python metrics. The endpoint needs a
long-lived access token belonging to an HA user, held in `home-assistant-prometheus`.

If the token is revoked, or the user that owns it is deleted, the target goes down with
`401`. Create a new one (*Profile → Security → Long-lived access tokens*) and encrypt it
without echoing it or writing it to disk in plaintext:

```sh
read -rs HA_TOKEN && printf 'apiVersion: v1\nkind: Secret\nmetadata:\n  name: home-assistant-prometheus\n  namespace: home-automation\ntype: Opaque\nstringData:\n  token: %s\n' "$HA_TOKEN" \
  | sops -e --filename-override kubernetes/apps/home-automation/home-assistant/prometheus-token.sops.yaml --input-type yaml --output-type yaml /dev/stdin \
  > kubernetes/apps/home-automation/home-assistant/prometheus-token.sops.yaml; unset HA_TOKEN
```

## Pairing

- **Zigbee** — *Permit join* in Zigbee2MQTT (or in Home Assistant on the Zigbee2MQTT bridge
  device), then reset the device into pairing mode. Join through a specific router device
  if the coordinator is far away.
- **Z-Wave** — *Control Panel → Manage nodes → Inclusion* in Z-Wave JS UI, or *Add device* in
  Home Assistant. S2 devices ask for the first five digits of the DSK printed on the device;
  Long Range devices can be added by scanning their SmartStart QR code.

## Backups and restore

| What | How | Where |
| --- | --- | --- |
| Home Assistant config, `.storage`, automations | Velero, pod volume `config` | `velero/` |
| Zigbee2MQTT data, incl. `coordinator_backup.json` and the device database | Velero, pod volume `data` | `velero/` |
| Z-Wave JS UI store, incl. the node cache and NVM backups | Velero, pod volume `store` | `velero/` |
| Recorder database | barman-cloud, daily base backup + WAL | `cnpg/home-assistant/` |
| Mosquitto retained messages | not backed up — rebuilt when the clients reconnect | — |

A full restore is the usual two moves: Flux redeploys the workloads, and Velero restores the
three volumes (see [Backups](./backups.md)). The database restores from barman — see
[Postgres → Restore](./postgres.md#restore). The radio keys come back from git with the
Secrets, so even a restore that loses a volume does not require re-pairing; the bridges just
rebuild their device lists by interviewing the network.

## Swapping a radio

Power the old radio off before the new one comes up. Two coordinators with the same network
parameters on the air at once confuse every device that hears both.

### Zigbee: ZBDongle-E → Dongle Max

Both are EmberZNet, so Zigbee2MQTT can carry the network across.

1. In the Dongle Max's web console, set it to Zigbee over Ethernet and note its TCP port. Give
   it a static lease on Trusted in `dhcp_leases` in `terraform/main.tf`.
2. Check that `coordinator_backup.json` in the Zigbee2MQTT volume is recent; Zigbee2MQTT
   writes it on start and periodically.
3. Point `ZIGBEE2MQTT_CONFIG_SERIAL_PORT` and the policy's `toCIDR`/port at the new
   radio, and push.
4. On start, Zigbee2MQTT finds the new coordinator blank and restores the network from the
   backup — key, PAN IDs, channel, and the coordinator's IEEE address. Devices carry on.
   If the IEEE address could not be written to the new chip, the log says so, and devices
   that do not rejoin on their own need re-pairing.

### Z-Wave: Dongle-PZG23 → Dongle-MZG23

Both are 800-series, so the NVM moves across without conversion.

1. In Z-Wave JS UI, take a fresh NVM backup (*Control Panel → Advanced actions → Backup*)
   and download it.
2. Set the MZG23 to Ethernet in its web console, note the port, and give it a static lease.
3. Point `ZWAVE_PORT` and the policy's `toCIDR`/port at it, and push.
4. Restore the NVM backup onto the new controller (*Advanced actions → Restore*). The
   security keys do not move with the NVM — they come from the `zwave-js-ui` Secret, unchanged.

Once both radios have moved, retire the Pi: drop its `trusted-30` lease and update
[Systems](../reference/systems.md).

## ESPHome (planned)

ESPHome devices go on the IoT VLAN, which has no internet. Home Assistant opens the
connection to each device's native API on TCP `6053`, so adding them takes:

- a forward rule in `terraform/modules/router/main.tf` from `Trusted_VLAN` to `IoT_VLAN` on
  TCP `6053` (pod traffic leaves SNAT'd to a node's Trusted address);
- an egress rule in `home-assistant/network-policy.yaml` to `10.69.40.0/24` on `6053`;
- a static lease per device, so each is added in Home Assistant by a stable address — mDNS
  discovery does not reach the pod.

## Troubleshooting

- **Zigbee2MQTT or Z-Wave JS UI crash-looping** — almost always the radio. Check the log for
  a refused or timed-out connection, then that the radio is powered and its endpoint matches
  both the Deployment and the policy. Policy drops are visible from the Cilium agent on the
  pod's node, since each agent only sees its own node's flows:

  ```bash
  NODE=$(kubectl -n home-automation get pod -l app=zigbee2mqtt -o jsonpath='{.items[0].spec.nodeName}')
  AGENT=$(kubectl -n kube-system get pod -l k8s-app=cilium --field-selector spec.nodeName="$NODE" -o name)
  kubectl -n kube-system exec "$AGENT" -- hubble observe --namespace home-automation --verdict DROPPED -f
  ```
- **Home Assistant answers `400: Bad Request`** — a proxy it does not trust sent
  `X-Forwarded-For`. The log says `A request from a reverse proxy was received from
  10.244.x.y`. Proxy trust is not in git: set it as in step 0 of
  [First-time setup](#first-time-setup), over a port-forward. If a trial change to the HTTP
  settings lapsed unconfirmed, the UI path works the same way.
- **Z-Wave JS UI login loops** — the session cookie is `Secure`, and Express only treats the
  request as HTTPS when it trusts the proxy that says so. `TRUST_PROXY` must cover the pod
  CIDR.
